# 📐 Общие Стандарты Разработки и Качества Кода (CODING_STANDARDS.md)

В проекте **Тихий ум** применяются строгие инженерные стандарты для обеспечения долговечности, читаемости и простоты поддержки кода между разными агентами и разработчиками.

---

## 1. 🏗️ Архитектура и Структура Кода
- **Принцип единственной ответственности (SRP):** Каждый модуль, класс или файл решает одну четко определенную задачу.
- **Слоистая архитектура:** Четко разделяйте:
  1. *Presentation Layer* (UI, API эндпоинты, контроллеры)
  2. *Business / Domain Logic* (сервисы, правила, вычисления)
  3. *Data Access Layer* (репозитории, модели данных, интеграции с внешними API)
- **Конфигурация через окружение (12-Factor App):** Все настройки (порты, урлы, таймауты, ключи) выносятся в переменные окружения через типизированные схемы конфигураций.

---

## 2. 🛡️ Строгая типизация и валидация
- **Python:**
  - Обязательное использование Type Hints во всех сигнатурах функций (`def calculate(total: float, discount: float = 0.0) -> float:`).
  - Использование Pydantic v2 или dataclasses для всех DTO и схем API.
  - Опциональные поля объявлять строго через `Optional[T] = None` или `T | None = None`.
- **TypeScript / JavaScript:**
  - Приоритет TypeScript со строгим режимом (`strict: true`).
  - Избегать необоснованного использования типа `any` (использовать `unknown` с валидацией zod/valibot).
- **Go / Rust / Other:**
  - Соблюдение идиоматических стандартов языка (`gofmt`, `cargo fmt`).

---

## 3. 🚨 Обработка Ошибок и Логирование
- **Информативные ошибки:** Любое исключение должно содержать понятное человеку сообщение с контекстом (какой ID искали, какой входной параметр не прошел валидацию).
- **Структурированное логирование:** Не использовать сырой `print()` или `console.log()` для боевого логирования. Использовать стандартные логгеры с уровнями (`INFO`, `WARNING`, `ERROR`).
- **Graceful Degradation:** Падение второстепенного сервиса (например, отправка статистики) не должно ронять критический путь пользователя.

---

## 4. 📝 Чистота кода и Документация
- **Самодокументируемый код:** Имена переменных и функций должны раскрывать их назначение (`fetch_active_user_orders()`, а не `get_data()`).
- **Сохранение существующих комментариев:** Никогда не удаляйте комментарии и docstrings, написанные предыдущими агентами, если они не противоречат изменениям.
- **Документирование публичных API:** Все публичные методы, эндпоинты и структуры должны снабжаться кратким описанием параметров и возвращаемых значений.

---

## 5. 🧪 Тестируемость
- Код должен проектироваться с возможностью легкого изолированного тестирования (Dependency Injection, передача зависимостей в конструктор/функцию).
- Любой исправленный критический баг должен сопровождаться регрессионным тестом, предотвращающим его повторное появление.
